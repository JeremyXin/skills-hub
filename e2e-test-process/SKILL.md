# 端到端自动化测试：通用流程与规范

> **本 skill 是规范库，不直接执行测试。** 执行入口是当前仓库的 `.claude/skills/<project>-e2e*/SKILL.md`，
> 它负责声明观测层清单（§2.1）、执行载体（§2.2）、环境档案位置、数据构造与清理方式。
> 当前仓库没有项目级 E2E skill 时，先按项目层要求建一个，不要直接照着本文跑测试。
>
> 本 skill 由人显式朗读，或由项目级 skill 按路径读取；`disable-model-invocation` 保证它不会被模型单独唤起后「只跑流程不做项目适配」。

## 1. 三条主线

1. **先想清楚测什么，再动手测。** 蓝图定骨架，用例定判据，数据定输入。
2. **每个验证点独立取证。** 入口返回不算证据；按项目声明的观测层交叉验证。
3. **产物落盘。** 蓝图、用例、数据、报告写进仓库，回归与排查可直接复用。

## 2. 项目适配契约

公共层只规定「必须声明什么」，具体值由项目 skill 给出。项目 skill 缺任一项，对应阶段不得执行。

### 2.1 观测层清单

| 层名 | 观测点 | 取证手段 | oracle 来源 |
|---|---|---|---|
| `<层名>` | | | |

规则：

- 层名由项目定义——服务端常见「接口 / 日志 / 消息 / 数据 / 指标」，推理管线常见 L0~L5；
- 层不必齐全，按实际存在的环节声明，省略的层在用例备注中说明；
- 每层的 oracle 必须独立于被测实现：需求、对外契约、人工标注、已审快照；**不能用被测代码的实际行为反推预期**；
- 「未发生」类断言必须写明检查范围覆盖了哪些层。

### 2.2 执行载体声明

| 项 | 声明内容 |
|---|---|
| 启动方式 | 部署到哪个环境 / 本地进程内启动 / CLI |
| 触发入口 | 接口、命令、手动触发器 |
| 版本确认 | 如何确认被测版本就是待测 commit |
| 日志取证 | 日志位置、过滤方式、时间窗 |
| 数据读取 | 只读通道与数据源 |
| 数据写入 | 执行开始时由用户选择的通道（二选一，写进报告，不进档案） |
| 清理方式 | 接口或 SQL，清理后如何回查 |
| 工具自检 | 登录态、入口连通性、只读探针命令 |

同一仓库允许多个载体（如「测试环境部署」与「本地进程内启动」），由项目 skill 分别声明，用例标注本次使用的载体。

## 3. 阶段总览

| 阶段 | 名称 | 产出 | 门禁 |
|---|---|---|---|
| S0 | 环境与前置 | 环境档案、入口准则检查结果 | 前置不满足 → 依赖它的用例记 BLOCKED |
| S1 | 输入梳理 | `REQ-1..n` | 每条可判定、可指回来源 |
| S2 | 测试蓝图 | 影响面、候选点、不测范围、用例骨架 | **用户确认后才写用例、造数据、执行** |
| S3 | 测试用例 | 用例、预期、覆盖矩阵 | 每条挂 REQ，预期可断言 |
| S4 | 测试数据 | 台账、构造与清理方案 | 数据带测试标记、可检索、可清理 |
| S5 | 执行与取证 | 逐例证据 | 不靠入口返回判定 |
| S6 | 判定与报告 | PASS/FAIL/BLOCKED + 逐例证据 | 口径见 §5 |
| S7 | 清理与归档 | 清理回查、缺陷记录、结论 | 未清理数据须登记保留原因 |

产物目录：`<repo>/docs/auto-test/<需求名>-<YYYYMMDD>/`（项目 skill 可声明等价目录）。

测试依据四来源缺一不可：需求文档（验收点）、接口/契约文档（触发与断言字段）、技术方案（链路、分支、配置、表）、分支提交历史（实际变更，防止漏测）。来源冲突时以用户最新确认口径为准，并在蓝图「待确认问题」留痕。

## 4. 三条硬约束

1. **只操作项目声明的环境。** 生产环境的任何写操作（部署、配置变更、命令执行）必须先向用户确认。
2. **读写分离。** 只读通道默认只读；写测试数据只能走执行开始时用户选定的通道，中途换通道需用户同意。测试专用接口必须带默认关闭的开关，生产不开放。
3. **触发会产生真实副作用**（写库、发消息、外呼）。只用带测试标记的数据，执行前确认，测完清理。

## 5. 判定与报告

按用例逐条给出 `PASS / FAIL / BLOCKED`：

- `FAIL`：取证结果与预期不符 → 记录失败层与实际值；
- `BLOCKED`：数据不满足、环境未就绪、工具不可用 → 写明阻塞原因，**不得记为 PASS**；
- 不要用「换数据重试」把 FAIL 变成 PASS，除非失败明确由数据引起且已记录。

**报告必须逐例给出「评测方式 + 具体证据 + 证据摘要」**：证据 = 命令或查询语句 + 实测值 + 时间窗，日志用原文摘录；只有一张结论总览表、没有可复核证据的报告视为未完成。报告结构见 `references/test-report-template.md`，出口准则见 `references/test-process-standard.md`。

**可选：结构化产物与可视化。** 项目 skill 若提供 `references/render-report.mjs` 与 `references/test-report-schema.md`，S6 需与 md 同轮产出 `-test-report.json` 并渲染同名 `.html`，三件一并提交，HTML 禁止手改；存在 blocker 告警时必须修复或改写结论。项目差异（层名、哪些层必须留 `request` / `response` 报文）写进 JSON 顶层 `reportConfig.payloadLayers`，渲染器本身不含项目词。未提供渲染器时本节不适用。

**可选：用例测试流程图。** 每条用例可带 `cases[].flow`，把执行链路画成 DAG 并把证据按节点下钻；无证据的服务端判断/日志步骤标 `unverified` 如实标注，不伪造报文。字段契约见 `references/test-report-schema.md` §4，排版与可读性约定见 `references/report-flow-design.md`（改渲染器布局前必读）。

## 6. 业界标准对齐

流程按 ISTQB 裁剪，只保留 E2E 真正用得上的部分。最容易被忽略的四条：

- **测试预期来自需求，不来自被测实现。** 读代码是为了找证据点，不是用代码行为反推预期。
- **测试点要能被需求回溯。** 每条用例挂 `REQ-x`，报告给覆盖矩阵，未覆盖项显式列出。
- **失败必须定位到层。** 「接口 200 但没效果」不是结论，要说清断在哪个观测层。
- **回归范围按影响面扩散。** 共享 topic / 表 / 接口的消费方都要评估。

## 7. 常见失败模式

| 现象 | 优先排查 |
|---|---|
| 触发成功但无后续日志 | 开关是否关闭、异步线程池是否拒绝、入口条件是否满足 |
| 日志停在「无待处理数据」 | 测试数据不满足前置条件，换数据不要改代码 |
| 落库有、下游无 | 生产端初始化、地址/配置、发送超时 |
| 新代码行为没出现 | 版本确认：被测版本是否真的包含待测 commit |
| 执行结果与档案描述不符 | 环境可能已变更，实测核实后再回写档案 |
| 用例全部 PASS 但线上仍出问题 | 只覆盖正向路径或断言过弱，回看不测范围与观测层 |
| 证据只有一句「已确认」 | 不可复现，补命令/查询语句 + 实测值 + 时间窗 |
