# 测试用例设计规范

> 约束 `docs/auto-test/<需求名>-<YYYYMMDD>/<需求名>-test-case.md` 的写法。
> 适用于服务端/管线类系统；UI 类用例不适用本规范。文中的「取证层」指项目 skill 观测层清单里的一层。
> 示例中的表名、topic、接口路径仅示意；实际取值以被测仓库的 `.claude/auto-test-profile.md` 与项目 skill 的载体声明为准。

## 1. 什么是一条测试用例

测试用例 = 为验证**一个明确的验收点**而设计的一组输入、前置条件和可断言的预期结果，是执行与判定不可再分的最小单元。

**一条用例只对应一个独立验收场景。** 它上承蓝图里的 `REQ-x`，下接一条可判定的执行记录。

拆分与合并的判定：

| 情况 | 处理 |
|---|---|
| 结果出口不同（命中 / 未命中、成功 / 拦截、落库 / 不落库） | 拆成两条 |
| 步骤与预期相同，只有输入数据不同 | 合并为一条，用参数表列多组数据 |
| 一条用例里出现两个「然后如果……则……」 | 拆 |
| 用例的预期是另一条用例预期的子集 | 合并，保留覆盖面大的那条 |

**反例**：「保存标签后验证接管信号链路」——一条里塞了接口、评分、落库、Kafka 四个判定，失败时无法定位，应拆成四条，或至少拆成接口/异步两段。

## 2. 标准结构

| 字段 | 必填 | 说明 |
|---|---|---|
| 用例 ID | 是 | `TC-<模块>-<3位序号>`，如 `TC-TAKEOVER-001`，全文档唯一且不复用 |
| 用例标题 | 是 | ≤50 字；格式「被测对象 + 操作 + 预期方向」；不含具体文案 |
| 核心程度 | 是 | `P0` / `P1` / `P2`，定义见 §4 |
| 关联需求点 | 是 | 蓝图中的 `REQ-x`，多条用「,」分隔 |
| 前置条件 | 是 | 静态状态断言，见 §3.2 |
| 测试数据 | 是 | 引用 `test-data.md` 的数据 ID（如 `D-01`），不在此重复完整数据 |
| 执行步骤 | 是 | 祈使句，一步一个原子操作，命令可复制执行 |
| 预期结果 | 是 | 可断言的「对象 + 状态 + 具体值」，标注取证层 |
| 证据点 | 是 | 本用例执行完必须留下的证据：响应字段、日志片段、topic/offset、SQL 结果 |
| 备注 | 否 | 依赖、风险、清理方式、已知限制 |

推荐的 Markdown 写法：

````markdown
### TC-TAKEOVER-001 评级 A 保存标签生成接管信号并发送 Kafka

- **核心程度**：P0
- **关联需求点**：REQ-1, REQ-3
- **前置条件**：测试环境 AI 与 CF 服务已部署含本需求的分支；`seller.takeover.template-variable.enabled` 已开启（执行时按日志/指标确认，不在准备阶段预先假定）；买家 `8613800000001` 已存在且未保存过标签；该买家存在 1 条未通知的待处理分发，关联任务处于投放中；评分接口地址可达
- **测试数据**：D-01（买家与分发）、D-02（投放中任务）
- **执行步骤**：
  1. 向 AI 服务发送 `POST /label/buyer/save`，请求体见下
  2. 轮询 AI 容器 `webapp.log`，按 `8613800000001` 过滤
  3. 执行 SQL 查询 `cf_buyer_takeover_signal`
- **预期结果**：
  1. 【接口层】HTTP 200，`downstreamSyncStatus` 不为 `failed`
  2. 【日志层】出现 `[接管信号] ...命中` 与 `保存接管信号成功`
  3. 【消息层】出现 `[接管信号Kafka] 发送成功`，topic 为 `seller-agent-take-over-topic`
  4. 【数据层】信号行 `notifyStatus=1`，`templateVariables` 非空
- **证据点**：响应 JSON、日志片段、topic/partition/offset、SQL 结果
- **备注**：执行前若该买家已存在信号，先调用 `/buyerTakeover/deleteByContactWa` 清理

```bash
curl -sS -m 30 -X POST "$AI_DOMAIN/label/buyer/save" \
  -H 'Content-Type: application/json' \
  -d '{"wa":"8613800000001","buyerRating":"A","categories":[1,2]}'
```
````

## 3. 字段编写规则

### 3.1 用例标题

**结构**：`[被测对象] + [操作] + [预期方向/场景条件]`

| 正确 | 问题 |
|---|---|
| 评级 A 保存标签生成接管信号 | — |
| 评级 C 保存标签不生成接管信号 | 反向出口，独立成条 |
| 已通知买家重复保存不新增信号 | 幂等场景 |
| 验证接管信号是否正常 | 用了「验证」「正常」，无信息量 |
| 保存标签后弹出「保存成功」并生成信号 | 塞入具体文案，标题过长 |

规则：

- ≤50 字，禁止换行；
- 不写「验证 / 检查 / 测试 / 查看」——那是测试动作，不是业务动作；
- 不写「成功 / 正常 / 符合预期」——没有判据；
- 不把预期文案写进标题（「弹窗文案为 X」放到预期结果）。

### 3.2 前置条件

**结构**：`[对象] + 已/为/处于 + [状态名词]`；多条件用「；」分隔。

前置条件是执行前的**静态快照**，每一条都应能改写成 `assert(...)`。它回答「世界现在是什么样」，不回答「我要做什么」。

服务端用例需要覆盖的五类：

| 类别 | 示例 |
|---|---|
| 环境 | 测试环境 AI 与 CF 服务已部署含本需求的分支；评分接口地址可达 |
| 功能状态 | 接管信号开关已开启（执行时按日志/指标确认，不预先假定取值） |
| 数据准备 | 买家 `8613800000001` 已存在；其存在 1 条未通知的待处理分发 |
| 账号 / 身份 | 商家 `orgId=TESTOrg001` 的账号 `accId=TESTAcc001` 处于投放中状态 |
| 版本 / 配置 | `cf_buyer_takeover_signal.templateVariables` 列已存在 |

写法对比：

| 错误写法 | 问题 | 正确写法 |
|---|---|---|
| 先登录后台再保存标签 | 写成了动作 | 测试账号处于已登录状态 |
| 确保开关打开 | 「确保」是断言不是状态 | 接管信号开关为开启 |
| 准备一条分发数据然后触发 | 动作混入 | 买家存在 1 条未通知的待处理分发 |
| 环境正常 | 不可判定 | 两个服务健康检查返回 200 |

规则：

- 只写影响本条预期成立的条件；每条前置都要能回答「去掉它，本条的哪个分支会变」；
- **前置写「状态」，台账写「怎么得到这个状态」**：例如前置写「买家存在 1 条未通知的待处理分发」，`test-data.md` 的 D-01 记录这条分发的键值、来源与清理方式；
- 通用执行准备（工具登录、域名、探针命令）不逐条复制，统一放 `test-data.md` 或报告的环境章节；
- 不要把「上一次执行成功」这种结果当前置。

### 3.3 执行步骤

**结构**：`序号. [操作动词] + [对象] + 可选（参数 / 命令）`

步骤是执行者主动发出的动作，动词开头，一步一个原子操作。命令要能直接复制运行，避免「调用接口」「查一下数据库」这类不可执行的描述。

| 动作类别 | 动词 |
|---|---|
| 调用 | 发送、触发、轮询 |
| 查询 | 执行 SQL、调用查询接口 |
| 等待 | 轮询直到…（写明超时与结束条件） |

规则：

- 不写「验证 / 检查 / 确认」——这些属预期结果；
- 异步流程必须写明结束条件（日志出现 / 超时 N 秒），不要只写「等待处理完成」。默认超时：同步接口 30s，异步链路 60s；「未发生」类断言至少观察一个完整调度周期 + 30s；
- 定时任务类需求写明触发方式（有手动触发接口则优先使用；无入口则等一个完整周期）与观察窗口；
- 步骤超过 10 步时考虑拆分用例；
- 涉及写操作时，步骤里要包含「记录原值」或「确认无存量数据」，便于回滚。

### 3.4 预期结果

**结构**：`【取证层】[对象] + [状态动词] + [具体值]`

预期结果描述执行后系统应处的状态，必须能被程序或人明确判真/假。

取证层命名以项目 skill 的观测层清单为准。下文用服务端项目的 **接口 / 日志 / 消息 / 数据 / 指标** 作为示例：前四层对应「调用 → 日志 → 消息 → 落库」，指标层是可选辅助；项目声明的层名不同时按项目层名替换。一条链路不一定各层齐全，按实际存在的环节取证；省略的层在备注中说明（如「同步接口，无消息层」）。

| 取证层 | 典型断言 |
|---|---|
| 接口层 | HTTP 200；`code=0`；`data.notifyStatus=1`；字段不存在 |
| 日志层 | 出现某 tag；不出现某异常栈；日志中 `topic=` 的值 |
| 消息层 | topic / key / 消息体键集合；某键不出现 |
| 数据层 | 行存在；`notifyStatus=1`；`templateVariables` 非空；行数增加 1 |
| 指标层 | Counter 增加；`result=success` |

规则：

- 有数字就写数字（「新增 1 行」「3 个键」），不写「若干」「多个」；
- 禁止「成功 / 正常 / 无异常 / 符合预期」；
- 涉及「不出现」的断言要写清楚检查范围（哪个日志文件、哪张表、哪个 topic）；
- 一条用例的预期可以分多层，但每一层都要能独立判定；不能因为接口 200 就跳过后面几层。

可判定性自检：每条预期能否改写成下面之一？

```
assertEqual(response.code, 0)
assertTrue(log.contains("[接管信号] ...命中"))
assertEqual(row.notifyStatus, 1)
assertFalse(message.containsKey("product1"))
assertTrue(counter("seller.takeover.template.variable.result{result=\"success\"}") > before)
```

### 3.5 测试数据与证据点

- 测试数据只写 ID 引用，完整字段（wa/orgId/accId/表名/初始状态/构造方式/清理方式）放 `test-data.md`；
- 证据点在执行时逐项收集，报告里按用例挂证据摘要，原始输出附在报告附录；
- 证据缺失视同 BLOCKED，不能按预期「推断」通过。

### 3.6 备注

写不属于前置、步骤、预期的补充信息：依赖的其他需求、已知限制、清理方式、历史缺陷、复测注意点。不要把预期结果复制到备注里，也不要在备注里放宽预期。

## 4. 核心程度（优先级）

| 级别 | 定义 | 服务端示例 | 失败后果 |
|---|---|---|---|
| P0 | 核心流程或核心验收点，功能不可用或核心数据错误 | 主链路生成信号并落库；消息体必含关键字段 | 功能不可用，必须修复后才能发布 |
| P1 | 主要分支、配置开关、常见边界 | 开关关闭时跳过评分；评级不满足时不生成信号 | 部分场景受影响，需评估后发布 |
| P2 | 低频异常、兼容、非核心字段 | 评分超时降级；非验收范围的重复保存 | 可延后修复，报告中记录 |

规则：

- 按**业务影响**判断，不按实现难度；
- **显式验收点不按「异常场景」自动降级**：幂等、开关关闭、降级路径若写入需求验收点，按业务影响定 P0/P1；只有在需求中未提及、顺带观察的才按 P2。同一场景在蓝图与用例中的级别必须一致；
- 不设固定比例，不为了凑 P0 而拔高；
- 冒烟测试是 P0 的子集，不等于「所有 P0」；
- 降级不是豁免：P2 失败也要记录，不能标记为「已知问题」后不追踪。

## 5. 设计方法

按需求选用，不要求每个方法都产出用例。方法用于**推导**测试点，预期仍以需求为准。

### 5.1 等价类划分

把输入域分成「系统行为相同」的若干类，每类取代表值。

```
buyerRating：有效类 {S, A, B} / 无效类 {C, D, 空, 非法值}
categories：有效类 {非空数组} / 无效类 {空数组, null}
```

一条用例覆盖一个等价类；多个无效类通常分别成条（避免一个无效值掩盖另一个）。

### 5.2 边界值分析

适用于数量、长度、时间窗口、分页上限。

```
候选商品数上限 5：测 4 / 5 / 6
评分超时 3000ms：测 2900 / 3000 / 3100（配合 mock 或故障注入）
```

没有故障注入能力时，边界用「可构造的真实数据」覆盖，不要为了边界去改配置。

### 5.3 判定表

多条件组合决定结果时使用。例如「评级 ∈ {S,A,B}」×「categories 非空」×「存在未通知分发」：

| 评级达标 | categories 非空 | 有未通知分发 | 预期 |
|---|---|---|---|
| 是 | 是 | 是 | 生成信号 |
| 是 | 是 | 否 | 不生成，日志「无未通知的待处理分发」 |
| 是 | 否 | 是 | 不生成（入口条件不满足） |
| 否 | — | — | 不生成 |

先列全组合，再按风险抽样；被裁掉的组合在蓝图中说明理由。

### 5.4 状态迁移

适用于状态位、调度任务、消息确认。

```
notifyStatus: 0（未通知） --发送成功--> 1（已通知）
              0 --发送失败--> 0（保持，可重试）
              1 --重复触发--> 1（不新增行）
```

每个迁移至少一条正向、一条非法迁移（如已通知再触发应被跳过）。

### 5.5 场景法

按业务流程串起主流程、备选流、异常流：

- 主流程：正常数据 → 预期结果；
- 备选流：不同配置/数据分支 → 不同出口；
- 异常流：下游失败、超时、空数据 → 降级行为。

E2E 链路优先用场景法，单元级分支用等价类/判定表更经济。

### 5.6 分支覆盖（辅助）

读代码确认 `if/switch` 后，检查每个分支是否有用例。**用途是查漏，不是生成预期**：

- 分支存在但需求未定义行为 → 进蓝图「待确认问题」，不自行编造；
- 分支不可达（已下线开关）→ 在蓝图写明不测理由。

## 6. 正反向配套

有正向用例时，通常需要一个反向出口：

| 正向 | 配套反向 |
|---|---|
| 条件满足 → 生成信号 | 条件不满足 → 不生成，且日志给出跳过原因 |
| 开关开启 → 调用评分 | 开关关闭 → 不调用，指标 `reason=disabled` |
| 消息成功 → 含商品键 | 评分失败 → 消息仍发送但无商品键（fail-open） |

反向用例的断言往往比正向更重要：**「没发生」比「发生了」更容易被误判为通过**，必须确认检查范围足够（查了日志、查了表、查了 topic）。

完整反向示例：

```markdown
### TC-TAKEOVER-004 模板变量开关关闭保存标签不调用评分且消息无商品键

- **核心程度**：P1
- **关联需求点**：REQ-2
- **前置条件**：`seller.takeover.template-variable.enabled` 已关闭（执行时按日志/指标确认）；买家 `8613800000001` 已存在且存在 1 条未通知的待处理分发；执行前该买家无信号记录
- **测试数据**：D-01
- **执行步骤**：
  1. 向 AI 服务发送 `POST /label/buyer/save`，请求体同 TC-TAKEOVER-001
  2. 轮询 AI 容器 `webapp.log` 中 `8613800000001` 相关日志，等待 60s
  3. 查询 `cf_buyer_takeover_signal` 中 `contactWa='8613800000001'` 的记录
- **预期结果**：
  1. 【接口层】HTTP 200
  2. 【日志层】出现 `[接管信号] ...命中` 与 `保存接管信号成功`；**不出现** `[卖家Agent接管模块][RESOLVE] 评分成功`
  3. 【消息层】在 `seller-agent-take-over-topic` 中按 key `8613800000001` 检查同批消息，`product1` / `product2` / `product` 三个键均不存在
  4. 【指标层】`seller.takeover.template.variable.result{reason="disabled"}` 计数 +1
- **证据点**：日志片段（含时间窗）、消息体、指标前后值
- **备注**：执行前记录指标基线；「不出现」的检查范围限定为本次触发时间点之后的日志与同批消息
```

注意反向用例的两个常见错误：一是只断言「没有报错」，没有指定检查范围；二是把开关关闭后「消息仍发送」误当成失败——需求是 fail-open，消息应照发，只是缺商品键。

## 7. 可追溯与覆盖

用例文档末尾必须给出矩阵：

```markdown
## 覆盖矩阵

| REQ | 蓝图测试点 | 覆盖用例 | 结论 |
|---|---|---|---|
| REQ-1 | BLP-01, BLP-02 | TC-TAKEOVER-001, TC-TAKEOVER-002 | 已覆盖 |
| REQ-2 | BLP-03, BLP-04, BLP-06 | TC-TAKEOVER-001, TC-TAKEOVER-003, TC-TAKEOVER-004 | 已覆盖 |
| REQ-3 | BLP-05 | TC-TAKEOVER-005 | 已覆盖 |
| REQ-4 | — | — | 未覆盖：测试环境无灰度白名单 |
```

未覆盖项必须写明原因，不能留空。新增/删除用例时同步矩阵。

## 8. 编写自查清单

- [ ] 每条用例只有一个验证目标，结果出口唯一；
- [ ] 标题 ≤50 字，无「验证 / 检查 / 正常 / 成功」；
- [ ] 前置条件全部是状态断言，多条件用「；」分隔；
- [ ] 前置只保留影响本条预期的条件，通用环境准备未逐条复制；
- [ ] 步骤是命令级动作，异步步骤有结束条件与超时；
- [ ] 预期结果逐层标注取证层，且都能改写成断言；
- [ ] 反向用例写明了检查范围；
- [ ] 每条用例都能挂到至少一个 REQ；
- [ ] 测试数据以 ID 引用，未在用例中重复完整数据；
- [ ] 覆盖矩阵完整，未覆盖项有原因。

## 9. 常见反模式

| 反模式 | 为什么错 | 修正 |
|---|---|---|
| 「接口返回 200，功能正常」 | 200 不代表异步链路成功 | 补日志、消息、落库断言 |
| 一条用例覆盖整条链路的所有分支 | 失败无法定位 | 按结果出口拆分，链路用一条 P0 串起来，分支各自成条 |
