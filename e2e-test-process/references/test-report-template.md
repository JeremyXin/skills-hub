# 测试报告模板

> 文件：`docs/auto-test/<需求名>-<YYYYMMDD>/<需求名>-test-report.md`
> 报告的唯一目的是让没参与执行的人能判断「这个需求能不能发」。所有结论必须能被证据支撑。
> 示例中的接口、表名、配置 key 仅示意；环境事实以被测仓库的 `.claude/auto-test-profile.md` 与项目 skill 的载体声明为准；写入通道在执行开始时由用户选择，并记入「环境基线」。

## 模板

```markdown
# <需求名> 测试报告

## 1. 基本信息

- 分支 / commit：
- 测试环境：环境名、载体（部署 / 本地启动 / CLI）、profile
- 环境基线：
  | 项 | 值 |
  |---|---|
  | 应用 | <profile:app> |
  | 部署 | <profile:deploy> |
  | commit | <sha> |
  | profile | test |
  | 写入通道 | sql-query / 测试接口（本次选择） |
| 测试专用接口 | 路径 + 开关 key（使用到时填写，否则删掉本行） |
- 跨仓库环境基线（profile §6 有关联仓库时填写，否则删掉本节）：
  | 仓库 | 应用/部署 | commit |
  |---|---|---|
  | <关联仓库> | <app> / <deploy> | <sha> |
- 配置基线（含本次变更与恢复）：
  | key | 改前 | 执行时 | 已恢复 |
  |---|---|---|---|
  | seller.takeover.template-variable.enabled | true | false | 是 |
- 执行时间 / 执行人：

## 2. 范围

- 覆盖需求点：REQ-1, REQ-2, REQ-3
- 不测范围及理由：
  | 内容 | 理由 |
  |---|---|
  | 评分模型准确率 | 非本次改动，算法侧负责 |

## 3. 执行统计

| 优先级 | 总数 | PASS | FAIL | BLOCKED |
|---|---|---|---|---|
| P0 | 4 | 3 | 1 | 0 |
| P1 | 3 | 3 | 0 | 0 |
| P2 | 2 | 1 | 0 | 1 |
| 合计 | 9 | 7 | 1 | 1 |

## 4. 用例结果

### 4.1 证据通道

> 层名按项目 skill 的观测层清单列出；下表用服务端项目示例。

| 层 | 取证方式 | 本轮取值 |
|---|---|---|
| 接口层（示例） | <curl / 测试客户端 / 调用记录> | |
| 日志层 | <日志文件与过滤方式> | |
| 消息层 | <topic / key / 消费方式> | |
| 数据层 | <只读通道与查询方式> | |
| 指标层 | <指标名 / 查询方式；未使用则删除本行> | |

### 4.2 总览

| TC | 结论 | 覆盖 REQ | 失败层 | 证据摘要 |
|---|---|---|---|---|
| TC-001 | PASS | REQ-1 | — | 接口 200；日志命中 X；DB status=1 |
| TC-003 | FAIL | REQ-2 | 消息层 | 消息缺少 product1（见 BUG-01） |
| TC-006 | BLOCKED | REQ-3 | — | 测试环境无灰度白名单 |

### 4.3 逐例证据

> 每条用例一节。只给总览表不算完成——人工复核只能依赖这一节，不能依赖执行者的口头结论。
> 证据必须可复现：给出命令或查询语句、实际返回值、以及时间窗（异步链路必须给时间窗）。

#### TC-001 <用例标题> —— PASS

- **对应实现**：<被测入口 / 类 / 方法 / 配置项；可选，用于说明这条用例验证的是哪段逻辑>
- **评测方式**：接口层 + 日志层 + 数据层（按实际使用的层写）
- **测试流程**：`开始 → 保存接口 → 查询商品表 → 调度触发 →[商品不存在]→ 取消回调 → 结束`
  （声明渲染器时，本节与 JSON 的 `cases[].flow` 或 `cases[].flowRef` 必须描述同一条链路；未声明渲染器时只写这一行）
- **具体证据**：
  1. 【接口层】`curl ...` → 响应 `{"code":0,...}`（时间）
  2. 【日志层】`<时间> <tag> contactWa=... 命中`（原文摘录，不改写）
  3. 【数据层】`SELECT notifyStatus, templateVariables FROM ... WHERE ...` → `1 | {...}`
  4. 【消息层】topic `<topic>` key `<key>` partition/offset，消息体关键字段 `...`
- **证据摘要**：<一句话：验证了什么、实际值是什么>

#### TC-003 <用例标题> —— FAIL

- **对应实现**：...
- **评测方式**：...
- **具体证据**：
  1. 【消息层】...
  2. 【日志层】...
- **失败分析**：预期 `<预期>`，实际 `<实际>`；失败层 = 消息层；关联 BUG-01

#### TC-006 <用例标题> —— BLOCKED

- **评测方式**：...
- **阻塞项**：<缺少的前置条件 / 不可用的工具>
- **已取得的证据**：<能拿到的部分；没有则写「无」>
- **补测条件**：<满足什么条件可补测；责任人>

## 5. 缺陷

| ID | 严重度 | 优先级 | 现象 | 影响 | 关联 TC | 状态 |
|---|---|---|---|---|---|---|
| BUG-01 | Major | P1 | 评分超时降级时消息缺少 product1 | 下游无法展示商品 | TC-003 | 已提 |

## 6. 未覆盖与风险

- REQ-4 未覆盖：测试环境无灰度白名单，需等配置后补测；
- 风险：评分接口为外部依赖，超时行为仅在测试环境验证，生产超时阈值需另行确认。

## 7. 数据清理

- 清理方式：调用 `/buyerTakeover/deleteByContactWa`；SQL cleanup 脚本；
- 影响行数：构造 2 行，清理 2 行，回查 0 行；
- 保留数据及原因：无。

**有条件发布**：P0 通过；BUG-01 需在发布前修复并复测 TC-003。

## 附录：原始产物（可选）

体积较大的原始输出（JUnit XML、完整响应体、查询导出、日志切片）存同目录 `evidence/`，命名 `<TC-ID>-<内容>.txt|json|xml`；正文 §4.3 摘录关键行并标注文件名。

> 附录不承担「能否复核」的职责——复核所需的关键证据必须在 §4.3 内可直接看到。
```

## 结构化产物与可视化（可选）

> 本节为可选能力：项目 skill 未声明渲染器时跳过，md 报告即为最终产物。

项目 skill 若提供 `references/render-report.mjs` 与 JSON 契约（`references/test-report-schema.md`），S6 必须：

1. 与 md 同轮产出 `-test-report.json`，字段按 schema，**断言必须写「预期 + 实测」**；
2. 运行渲染器生成同名 `.html`，打开自查完整性告警；
3. md / json / html 三件一并提交，HTML 禁止手改；
4. 存在 blocker 告警时必须修复或改写结论，不能只关告警。

项目差异（层名、哪些层必须留 `request` / `response` 报文）写进报告 JSON 顶层，渲染器不含任何项目词：

```json
"reportConfig": { "payloadLayers": ["<层名>", "..."] }
```

`payloadLayers` 未声明时，渲染器不检查报文，其余告警规则照常执行。

### 测试流程（`cases[].flow` / `flowTemplates` + `flowRef`，可选）

声明渲染器时，建议给每条用例补流程（否则该例在页面上没有流程图，证据仍按层分组展示）。
同一条业务链路被多条用例覆盖时，**优先用模板复用**，不要在每条用例里复制节点：

1. 报告顶层 `flowTemplates` 定义一次完整链路（节点、边、所有分支终态）；项目 skill 可提供模板文件作为事实源。
2. 每条用例只写 `flowRef: { template, branch, evidenceRefs }`，用 `branch` 选择当前用例走过的路径，
   `evidenceRefs` 把证据挂到当前分支的节点。
3. 只被一条用例使用的一次性链路，才直接写内联 `flow.nodes` / `flow.edges`。
4. 先按 §4.3 的「测试流程」一行写完链路描述（`A → B →[条件]→ C`），再翻译成模板/分支；
   Markdown 仍是事实源。
5. 节点类型按动作性质选：接口=http、表查询=sql、调度=schedule、下游回调=callback、配置=config、
   服务端判断=decision、日志=log（无取证时标 `unverified` + `note`）。
6. 证据按节点挂载 `evidenceRefs`，不新增证据；设计上无证据的步骤标 `unverified`，**不得伪造 payload**。
7. 重试画前向链，不画回边。

字段契约见 `test-report-schema.md` §4，排版约定见 `report-flow-design.md` §8。

## 填写规则

| 章节 | 规则 |
|---|---|
| 基本信息 | commit 必须能对应到待测分支；配置基线列全部变更，未恢复的显式标「否」 |
| 范围 | 与蓝图保持一致；范围变更要说明原因 |
| 执行统计 | BLOCKED 单独计数，不能并进 PASS 或 FAIL |
| 用例结果 | 必须包含「证据通道 + 总览 + 逐例证据」；只有总览表视为未完成 |
| 逐例证据 | 每条用例写「评测方式 / 测试流程 / 具体证据 / 证据摘要」；证据 = 命令或查询语句 + 实测值 + 时间窗 |
| 测试流程 | 一行链式描述（`A → B →[条件]→ C`），与 JSON `flow` / `flowRef` 一一对应；无证据的步骤标「未取证」并写原因 |
| 具体证据 | 日志用原文摘录不改写；异步链路必须给时间窗；「未发生」类断言写明检查范围 |
| 对应实现 | 可选；用于定位被测逻辑，**不得用于反推预期** |
| FAIL 用例 | 额外给「失败分析」：预期 vs 实际、失败层、关联缺陷 |
| BLOCKED 用例 | 额外给「阻塞项 + 已取得证据 + 补测条件」；已取得的证据不得省略 |
| 缺陷 | 严重度与优先级分列；关联 TC 便于回归 |
| 未覆盖与风险 | 不允许留空，写「无」也要写 |
| 数据清理 | 构造行数与清理行数对得上 |
| 结论 | 三选一，不能写「基本没问题」 |

## 结论判定

| 结论 | 条件 |
|---|---|
| 可发布 | 出口准则全部满足：P0 全部 PASS，无未闭环 Critical / Major |
| 有条件发布 | P0 无 FAIL，且无未闭环 Critical；存在已评估的 Major 或 P1 失败，或 P0 有 BLOCKED 但阻塞原因已定位、补测条件与责任人明确 |
| 不可发布 | P0 存在 FAIL、存在未闭环 Critical、核心链路无证据，或 P0 阻塞原因无法定位 / 无补测路径 |

> P0 为 BLOCKED 时不得判「可发布」：能定位阻塞并给出补测条件记「有条件发布」，否则记「不可发布」。责任人字段缺失时用「待指定」占位，不能省略。

## 常见问题

| 问题 | 后果 | 修正 |
|---|---|---|
| 只写「全部通过」不列用例 | 无法复核 | 逐条列结论与证据摘要 |
| 用例结果只有一张总览表 | 人工无法复核，结论只能靠执行者自述 | 按 §4.3 逐例补「评测方式 + 具体证据 + 证据摘要」 |
| 证据只写「已确认 / 符合预期」 | 不可复现 | 给命令或查询语句 + 实测值 + 时间窗 |
| 流程图标了「未取证」却没写原因 | 读者无法区分「没取」和「取不到」 | `note` 写清缺失通道，如「应用日志不可读」 |
| FAIL 没有失败层 | 定位从零开始 | 标注接口/日志/消息/数据/指标 |
| 把 BLOCKED 记成 PASS | 掩盖未验证范围 | 单列并写阻塞原因 |
| 配置改了没恢复 | 污染环境，后续执行结果不可信 | 恢复并回查，报告留痕 |
| 结论含糊 | 决策无法做出 | 三选一，写明条件 |
