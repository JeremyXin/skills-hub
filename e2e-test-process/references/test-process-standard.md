# 测试流程与准则（业界标准对齐）

> 本文件按 ISTQB 测试过程裁剪而来，只保留 E2E 自动化真正用得上的部分。
> 本文说明「对应关系、准则、判定标准」，不重复 SOP 的操作步骤。

## 1. 与 ISTQB 测试过程的映射

ISTQB 把测试过程分为七个活动。本 skill 的对应关系：

| ISTQB 活动 | 本 SOP | 产物 |
|---|---|---|
| 测试计划 | 前置检查 + 输入梳理 | 范围、环境、资源确认 |
| 测试监控与控制 | 执行取证 + 判定 | 实时结论、偏差处理 |
| 测试分析（测什么） | 测试蓝图 | `REQ-x`、不测范围 |
| 测试设计（怎么测） | 测试用例设计 | 用例、预期、覆盖矩阵 |
| 测试实现（准备与组装） | 测试数据准备 + 脚本化 | 数据台账、触发命令、轮询脚本 |
| 测试执行 | 触发 → 取证 | 按观测层取证 |
| 测试完成 | 报告 + 清理 + 归档 | 测试报告、缺陷记录、清理结果 |

关键点：**分析和设计是两件事**。蓝图回答「测什么」，用例回答「怎么测、怎么判」。合并成一步的结果通常是「按实现写用例」，覆盖不到需求本身。

## 2. 测试依据与判定基准

ISTQB 的 *test basis* 是本流程的输入，*test oracle* 是判定标准。

| 概念 | 在本流程中的含义 |
|---|---|
| 测试依据 | PRD、接口文档、技术方案、已确认的业务口径 |
| 判定基准（oracle） | 需求定义的预期行为，不是代码的实际行为 |
| 代码的作用 | 定位证据点（日志 tag、表、topic、分支），**不是**生成预期 |

**最常见的失效模式**：读代码后把「代码会做什么」写成预期。这样测出来的用例只能发现崩溃类缺陷，发现不了「代码实现与需求不一致」——而那恰恰是需求验证的主要目的。

正确做法：

1. 从需求写出预期；
2. 从代码找该预期应该留下的证据；
3. 证据对不上时，先判断是实现问题还是需求理解问题，不要直接改预期迁就实现。

## 3. 测试层次与类型

| 维度 | 本 skill 的定位 |
|---|---|
| 层次 | 系统级（跨服务 E2E），不替代单元测试和集成测试 |
| 类型 | 功能测试 + 变更相关测试（确认测试 + 回归测试） |
| 不覆盖 | 性能、安全、兼容性、可用性（需要时另立专项） |

系统级测试的局限：定位粒度粗、环境依赖强、执行成本高。所以单元/集成层能覆盖的分支，不要全压在 E2E 上——E2E 聚焦跨服务的链路与关键业务规则。

## 4. 入口准则

所有条件满足才进入执行；不满足时记录为 BLOCKED，不要强行执行后把失败归因于代码。

- [ ] 待测版本已按项目 skill 声明的载体就绪，版本与待测分支的 commit 一致（确认方式见载体声明）
- [ ] DDL / migration 已在目标库执行
- [ ] 已记录关键配置基线；业务开关状态以运行时行为与日志判断，确需变更时按 §10 流程执行（不在入口阶段预判开关值）
- [ ] 依赖服务（评分接口、下游消费者等）可达
- [ ] 写入通道已选定（项目声明的通道形态：测试接口 / 数据库工具 / SQL 脚本交用户执行），或已确认本轮只读
- [ ] P0 用例的测试数据可构造，或已发现存量数据
- [ ] 每条 P0 用例的预期结果有明确判据
- [ ] 项目 skill 声明的工具登录态、入口连通性、只读通道自检通过

## 5. 出口准则

满足以下条件才能宣布测试完成：

- [ ] P0 用例全部 PASS；
- [ ] P1 无未评估的失败（失败项已评估影响并给出结论）；
- [ ] 无未闭环的 Critical / Major 缺陷；
- [ ] 每条用例都有对应证据，失败项已定位到取证层；
- [ ] 覆盖矩阵完整，未覆盖范围与原因已列出；
- [ ] 测试数据已清理，或已标注保留原因；
- [ ] 报告已落盘，结论明确（可发布 / 有条件发布 / 不可发布）。

「跑完了」不等于「测试完成」。没有出口准则的测试会无限延长，或者在有未闭环缺陷时被误判为通过。

## 6. 风险驱动

优先级应来自风险，而不是来自「先写哪条顺手」。风险 = 发生可能性 × 影响程度。

| 风险来源 | 提高优先级的信号 |
|---|---|
| 变更集中 | 本次 diff 改动大、新分支多 |
| 链路复杂 | 异步 + 多数据源 + 外部调用 |
| 数据敏感 | 涉及资金、消息外发、状态终态 |
| 历史缺陷 | 该模块过去出过问题（缺陷聚集） |
| 共享依赖 | topic / 表 / 接口有多个消费方 |

对应做法：变更密集处多设计分支用例；共享依赖必须评估消费方；历史问题模块补回归用例。

## 7. 可追溯矩阵

从需求到结论的单向可查链：

```
REQ-1 ──> BLP-01 ──> TC-TAKEOVER-001 ──> 证据 ──> PASS
```

报告中必须给出 REQ → TC → 结论的矩阵。作用：

- 证明每个需求点被覆盖；
- 需求变更时能快速定位受影响的用例；
- 缺陷出现时能反查影响面。

没有矩阵时，用例数量再多也无法回答「这个需求测了没有」。

## 8. 缺陷管理

### 8.1 缺陷报告要素

| 字段 | 内容 |
|---|---|
| 标题 | 现象 + 影响，不写「XX 有问题」 |
| 严重度 | Critical / Major / Minor：对系统的影响 |
| 优先级 | 修复顺序：由业务影响决定 |
| 环境 | 应用、部署、commit、配置 |
| 前置条件 | 复现所需的静态状态 |
| 复现步骤 | 命令级，可直接照做 |
| 预期 / 实际 | 分别写，不合并 |
| 证据 | 日志片段、SQL 结果、消息、响应 |
| 失败层 | 接口 / 日志 / 消息 / 数据 / 指标 |
| 关联用例 | TC ID |

严重度与优先级是两个维度：严重度高但影响面小的可以低优先级；严重度低但阻塞主流程的也可以高优先级。不要混用。

### 8.2 复测与回归

- **确认测试（retest）**：修复后只重跑失败用例，验证缺陷已解决；
- **回归测试（regression）**：确认修复没有破坏其他功能，范围按影响面扩散；
- 复测必须回到同一环境、同一数据条件，否则结果不可比。

## 9. 回归范围

变更相关测试的范围由影响分析决定，不是「把所有用例再跑一遍」。

评估维度：

| 维度 | 要问的问题 |
|---|---|
| 直接改动 | 哪些接口、分支、表、topic 变了 |
| 上游 | 谁会调用这个接口 / 谁生产这条消息 |
| 下游 | 谁消费这条消息 / 谁读这张表 |
| 共享配置 | 有没有其他功能共用同一个开关或 key |
| 调度 | 改动是否影响定时任务的下一次触发；有手动触发入口优先手动触发 |
| 相邻功能 | 同一模块里没有直接改动但共用代码路径的功能 |

标记为回归的用例通常包括：P0 全部 + 改动影响面覆盖的 P1 + 历史缺陷对应用例。

## 10. 测试环境与配置管理

- 执行前记录环境基线：应用名、部署标识、commit、profile、本次写入通道、关键配置值；
- 配置变更要记录「改前 / 改后 / 恢复」，不能只改不记；
- 同一批次内不要随意改配置，否则前后用例结果不可比；
- 环境异常（重启、发布）后，已执行用例的结论需要重新确认。

### 验证开关分支时的配置变更

「开关关闭 / 打开」是合法的测试手段，但必须按下面流程走，否则等于用配置掩盖代码问题：

1. **明确变更点**：key、当前值、目标值、依赖该 key 的用例列表；
2. **由用户执行或授权**：配置中心（具体平台以项目声明为准）变更前征得确认，不自行改生产或他人负责的 namespace；
3. **确认生效方式**：业务开关一般实时读取；线程池容量、连接池等启动期配置需重启才生效——判断依据是代码中 `@Value` / `@ConfigurationProperties` 的位置；
4. **确认已生效**：变更后先跑一条最轻的用例（或查 debug 日志）验证读到新值，再执行正式用例；
5. **恢复并回查**：本批次结束立即恢复原值，回查确认，记录恢复时间；
6. **报告留痕**：报告「配置基线」章节列出本次所有变更与恢复情况；未恢复的必须标注。

> 与 `test-data-spec.md` §9 的关系：禁止的是「为让用例通过而改配置」，允许的是「为覆盖开关分支而改配置」。区分标准是——改完是否改变了被测代码的行为预期。

## 11. 测试报告

模板见 `test-report-template.md`。报告至少包含：基本信息、范围、执行统计、用例结果、缺陷、未覆盖与风险、数据清理、结论。缺任何一节都不能算完整报告。

## 12. 常见无效测试（假阳性）

| 假阳性模式 | 为什么无效 | 正确做法 |
|---|---|---|
| 只断言 HTTP 200 | 异步链路可能整条断了 | 补日志、消息、落库断言 |
| 只看日志出现关键字 | 可能命中的是别的请求 | 加业务 key 与时间窗过滤 |
| 数据本身不满足前置 | 走的是跳过分支，不是被测分支 | 先核对全部前置条件 |
| 用 sleep 等待 | 环境慢时假失败，快时假通过 | 轮询到条件或超时 |
| 失败后换数据重跑直到通过 | 掩盖缺陷 | 记录 FAIL，确认原因再重跑并注明 |
| 检查范围不足的「未发生」断言 | 没查全就断言不存在 | 明确查了哪些日志、表、topic |
| 直连数据库改结果字段 | 等于自己写答案 | 只构造输入，不构造输出 |

## 13. 测试独立性与七条原则

ISTQB 七条测试原则在本流程中的落点：

| 原则 | 落点 |
|---|---|
| 测试显示缺陷存在，不能证明缺陷不存在 | 报告写「已覆盖范围」，不写「功能无问题」 |
| 穷尽测试不可能 | 用风险驱动取舍，蓝图写明不测范围 |
| 尽早测试 | 需求评审阶段就开始梳理验收点，不等部署 |
| 缺陷聚集 | 历史问题模块与高变更模块多设计用例 |
| 杀虫剂悖论 | 同一批用例长期不变会失效，定期补充数据与场景 |
| 测试依赖上下文 | 本流程只适用于 E2E，不套用到其他场景 |
| 「无缺陷」谬误 | 用例全 PASS 不代表满足需求，要回到 REQ 逐条确认 |

**独立性**：设计用例的人与实际写实现的人视角不同时，更容易发现需求偏差。对 AI 执行而言，等价的做法是——预期只从需求取，不从实现取；报告中区分「代码符合实现」与「代码符合需求」。

## 14. 探索式测试（补充手段）

蓝图和用例覆盖的是已知范围。执行过程中遇到意外现象时，用限时会话补充：

- 目标（charter）：一句话说明这次探索什么风险；
- 时间盒：15–30 分钟；
- 记录：发现了什么、是否转成正式用例、是否登记缺陷；
- 探索发现的新场景回补蓝图与用例，不要只留在对话里。

用途是发现「用例没想到的风险」，不能替代正式用例，也不能用来给未覆盖范围背书。
