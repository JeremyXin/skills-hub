# 测试数据规范

> 约束 `docs/auto-test/<需求名>-<YYYYMMDD>/<需求名>-test-data.md` 与配套 SQL 脚本。
> 目标：数据可复现、可识别、可清理；不污染测试环境里的他人数据。
> 示例中的库名、表名、数据源名仅示意；环境事实以被测仓库的 `.claude/auto-test-profile.md` 为准，通道名称与形态以项目 skill 的载体声明为准。写入与清理通道不写档案，由用户在每次执行开始时选择。

## 1. 基本原则

1. **优先存量，其次构造。** 能直接找到满足条件的现有数据，就不要造新数据。
2. **不可逆数据不造。** 删除、覆盖、触发真实外发的操作，先确认影响范围。
3. **构造的数据必须一眼可识别。** 任何人为写入的字段都要带测试标记，便于检索和清理。
4. **被测结果不能靠数据构造。** 不能为了「让用例通过」直接把被测逻辑该写的结果写进库。
5. **写入前记录原值。** 需要修改已有记录时，先把原值记进台账，否则无法回滚。

## 2. 数据来源优先级

| 优先级 | 方式 | 适用 | 注意 |
|---|---|---|---|
| 1 | 存量数据发现 | 满足前置条件的现成记录 | 触发前把命中的记录写进台账 |
| 2 | 测试接口 / 业务接口写入 | 用户选择「测试接口」通道；有创建接口的数据，或需要走真实业务逻辑 | 优先；副作用可控、可清理；路径取自 SOP §1 的接口文档或用户确认；文档缺该接口时先提测试专用接口草案（§10），不猜 |
| 3 | sql-query 写入 | 用户选择「sql-query」通道，并提供可写数据源/库 | 数据源名与库由用户提供；只写前置状态；不可直连库不适用 |
| 4 | 生成 SQL 脚本人工执行 | 用户选 sql-query 但只能人工执行，或需要 DBA 审核 | 脚本含 cleanup，执行结果由用户回传 |
| — | 只读 | 用户明确只读 | 只发现存量数据，不构造；前置不满足时换数据或记 BLOCKED |

**写入与清理通道由用户在每次执行开始时选择，二选一：数据库工具（如 `sql-query`）或测试接口（名称与形态以项目声明为准）。** 不写进档案；中途换通道需用户同意。只读通道默认只读，任何 DML/DDL 都会失败。写入时在台账中注明「通道 + 数据源/接口 + 执行人」。写入报错先判断原因：连通/权限类先按 §6 产出 SQL 脚本交用户执行，用户也无法执行时才记 BLOCKED；确认仅当前通道不可用时，经用户同意才换另一个通道。

## 3. 存量数据发现

标准路径（以接管信号为例，表名与接口来自档案 §4.1 / §4.2，其他需求按同样思路替换）：

```
只读通道选候选（如 buyer_label 中评级 S/A/B 且 categories 非空）
  → 调档案登记的查询接口，挑有分发、无信号记录的
  → 调查询接口或只读通道确认关联数据（商品、任务状态）
  → 记录命中记录 → 再触发业务接口
```

规则：

- 发现阶段只做 GET 与只读 SQL；
- 不可直连库只能查档案 §4.2 登记的接口；未登记的，该候选记 BLOCKED，不要试接口路径；
- 每个候选记录必须核对**全部**前置条件，不能只核对第一个就触发；
- 命中记录（wa / orgId / accId / taskId / 行 ID）写入台账，否则出错时无法区分代码问题还是数据问题。

## 4. 构造数据的测试标记

所有人为写入的数据都必须能被一条查询或一次 grep 找出来。

### 4.1 标记方式

号段与前缀以档案 §5「测试数据约定」为准；档案未约定时用下面的默认值。

| 数据类型 | 标记规则 | 示例 |
|---|---|---|
| 买家 wa / contactWa | 使用团队约定的测试号段；未约定时取 `86` + `138000000` + 两位序号 | `8613800000001` |
| 商家 orgId / accId | 前缀 `TEST` + 需求缩写 | `TESTOrgTakeover01`、`TESTAccTakeover01` |
| 文本字段（名称、备注、标题） | 前缀 `AUTOTEST_<需求缩写>_`；字段允许中文时用 `测试_<需求缩写>_` | `AUTOTEST_TAKEOVER_案例A` |
| 需要唯一的值 | 前缀 + 时间戳或序号，避免与历史执行冲突 | `AUTOTEST_TAKEOVER_20261117_01` |
| 有来源/渠道字段的表 | 写 `autotest` | `source=autotest` |
| 枚举 / 状态字段（无法打前缀） | 不直接打标；通过关联的测试号段、文本字段或主键定位，台账登记行 ID | `id=TESTLead001`（关联测试买家） |

**禁止**使用真实用户号码或真实商家 ID 做写入测试——测试环境的 Kafka、短信、消息推送可能连接真实通道。

### 4.2 可检索性检查

写入后立即执行一次检索，确认能精确捞出全部构造数据：

```sql
-- 库名与表名取自档案 §4.1
SELECT id, contactWa, orgId, createTime
FROM <profile:read.schema>.<table>
WHERE contactWa = '8613800000001';
```

检索不到说明标记没写进去或写错了表——先修正，不要继续执行。目标库不可直连时，改用档案 §4.2 登记的查询接口按同一组键值回查；未登记查询接口则该步骤记 BLOCKED。

## 5. 数据台账

文件：`<需求名>-test-data.md`

```markdown
# <需求名> 测试数据台账

- 环境：test
- 执行批次：2026-11-17 / 第 1 次

## 数据清单

| ID | 关联用例 | 对象 | 关键键值 | 初始状态 | 构造方式 | 通道 | 清理方式 | 已清理 |
|---|---|---|---|---|---|---|---|---|
| D-01 | TC-TAKEOVER-001 | 买家 | wa=8613800000001 | 无标签、有 1 条未通知分发 | 存量发现 | 查询接口 | 无需清理 | — |
| D-02 | TC-TAKEOVER-001 | 投放任务 | taskId=TESTTask001 | 投放中、已关联 D-01 | 业务接口创建 | 测试接口 `POST /cowork_platform/...` | `DELETE /...` | 否 |
| D-03 | TC-TAKEOVER-003 | 信号 | contactWa=8613800000002 | notifyStatus=0 | sql-query 写入 | `sql-query`（数据源由用户提供） | `DELETE FROM ...` | 否 |

## 修改过的存量数据

| 对象 | 字段 | 原值 | 新值 | 恢复方式 | 已恢复 |
|---|---|---|---|---|---|
| 信号 123 | notifyStatus | 0 | 1 | 重新置 0 | 否 |

## 执行记录

- 2026-11-17 10:12 执行 `test-data.sql`，影响 2 行
- 2026-11-17 11:30 执行 `cleanup.sql`，影响 2 行，回查 0 行
```

台账是清理的依据。没有登记的数据视为残留。

## 6. SQL 脚本规范

当走通道 4 时，产出两个文件：

```
test-data.sql      构造数据
cleanup-test-data.sql  清理数据
```

要求：

- 脚本头部注明环境、库、数据源（环境取自档案，库/数据源由用户提供）、作者、执行方式、影响范围；
- 每条语句带显式列名，不使用 `SELECT *`；
- 构造与清理一一对应，清理条件与构造条件使用同一组键值；
- 不使用 `DELETE ... WHERE 1=1`、`UPDATE` 无 `WHERE` 这类全表操作；
- 执行前后各给一条核对 SQL（`SELECT COUNT(*)` 或按键查询）；
- 脚本本身不改表结构，DDL 单独走 migration 流程。

```sql
-- 环境：<profile:env> / <本次写库（用户提供）>
-- 用途：为 TC-TAKEOVER-003 构造一条未通知信号（示例，表名与列名以实测为准）
-- 执行人：<姓名>    执行时间：<时间>

INSERT INTO <本次写库>.cf_buyer_takeover_signal (contactWa, orgId, accId, inquiryId, notifyStatus, createTime, updateTime)
VALUES ('8613800000002', 'TESTOrgTakeover01', 'TESTAccTakeover01', 'TESTInquiry001', 0, NOW(), NOW());
```

## 7. 清理

- 优先测试接口 / 业务删除接口，其次 `sql-query` 或 cleanup SQL；
- 清理后必须回查，确认影响行数与预期一致；走业务接口清理时，用同一查询接口或只读通道按同一组键值回查；
- 无法清理的数据（如已发消息、已发外呼）在台账标「保留」并写明原因与影响面；
- 跨用例共享的数据在最后一条用例执行完再清理，不要中途删掉导致后续用例失败。

## 8. 幂等与重复执行

- 触发前先查目标记录状态：已通知的信号重复触发不会新增行，但会被误判为「没有生成」→ 先清理或换数据；
- 用户未提供写通道且未选择「SQL 脚本交用户执行」时，不进入构造流程，前置不满足直接换数据或记 BLOCKED（见 §2）。
- 同一批次重复执行时，台账开新的一节（第 2 次），不要覆盖上一次记录；
- 唯一键冲突优先换测试标记的序号，不要删除他人数据来腾位置。

## 9. 禁止事项

| 禁止 | 原因 |
|---|---|
| 使用真实用户号码 / 商家 ID | 可能触发真实外发 |
| 直接改被测逻辑应产出的结果字段 | 等于自己写答案 |
| 无 `WHERE` 的 UPDATE / DELETE | 污染测试环境 |
| 在不可直连库上用 sql-query 写 | 不可达；这类库也不支持 `ON DUPLICATE KEY UPDATE`，只能走应用接口 |
| 测试专用接口在生产可达 | 测试专用接口必须带默认关闭的配置开关（§10）；无开关的写入/删除接口不得合入 |
| 修改配置中心配置让用例通过 | 掩盖代码问题。**例外**：为验证开关分支而变更配置是允许的，但必须记录改前/改后、确认生效、测完恢复并回查（见 `test-process-standard.md` §10） |

## 10. 测试专用写/清理接口

现有业务接口和写入通道都无法构造或清理测试数据时，不要绕业务直接改表，也不要临时加一个生产可达的接口。

### 10.1 何时提

| 场景 | 例子 |
|---|---|
| 需要写入业务接口不开放的前置状态 | 直接往 `wa_cloud_message` 写一条待处理消息 |
| 需要物理清理测试数据，但没有删除接口 | 按测试号段删除 `cf_buyer_takeover_signal` 测试行 |
| 需要绕过异步/定时触发立即执行一次链路 | 手动触发某个 `@Scheduled` 任务 |

### 10.2 流程

1. **先出草案**：接口路径、HTTP 方法、入参、副作用、返回、清理能力、开关 key、影响表；
2. **用户确认**：新增接口属于代码变更，必须由用户确认后才实现，不在测试执行中顺手加代码；
3. **按 10.3 实现**；
4. **登记**：接口路径与开关 key 写进测试数据台账；报告中「环境基线」记「写入通道 + 测试专用接口路径」，清理方式记入「数据清理」章节。

### 10.3 实现约束（必须全部满足）

- **配置开关默认关闭**：用启动期条件装配（Spring 示例：`@ConditionalOnProperty(name = "<feature>.test-api.enabled", havingValue = "true", matchIfMissing = false)`，其他技术栈用等价机制）；生产配置不出现该 key；
- **生产不可达**：开关关闭时 Controller/Bean 不注册，接口返回 404，而不是 403 或业务报错；
- **注释写明用途**：类与接口标注「测试专用接口：仅测试环境开启，生产禁用」，并注明开关 key；
- **路径集中**：统一放 `/test/**` 或独立 `XxxTestController`，不与业务接口混用；
- **只接受测试标记**：写/删条件必须带测试号段或测试前缀，禁止按真实用户号码操作、禁止全表操作；
- **删除幂等**：清理接口按同一组键值重复调用结果一致，返回影响行数；
- **不改被测结果**：不得提供直接写入被测逻辑应产出字段的能力（等于自写答案）；
- **测试环境的开启方式**：开关 key 在测试环境由用户通过配置中心或测试 profile 打开，不自行修改生产配置；生产配置不出现该 key。

### 10.4 禁止

| 禁止 | 原因 |
|---|---|
| 无开关、生产可达的写/删接口 | 线上数据污染风险 |
| 用测试接口绕过业务校验、直接改核心表 | 测试结论失真（边界：允许写**输入型前置状态**，如一条待处理消息；禁止写被测逻辑应产出的结果字段） |
| 未经用户确认新增接口 | 超出测试范围，属于代码变更 |
| 把测试专用接口的开关默认值设为 true | 上线即暴露 |
| 测试数据留在环境里不登记 | 无法清理，干扰后续执行 |
