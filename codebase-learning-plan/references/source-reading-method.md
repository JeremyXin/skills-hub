# 源码阅读方法论

生成学习计划时按本文件做取舍。目标是「7 天后能改代码」，不是「读完所有文件」。

## 1. 如何选模块

按「改动一个需求要碰哪些地方」选，而不是按目录完整度选。

优先级排序：

1. **入口层**：CLI/HTTP/消息消费者 —— 理解程序如何被唤起
2. **编排层**：service/usecase —— 理解业务主流程
3. **数据/状态层**：model/repository/cache —— 理解数据形状与生命周期
4. **适配层**：client/adapter/gateway —— 理解外部依赖与错误边界
5. **横切层**：config/auth/error/logging/audit —— 理解全局约束
6. **测试与工具**：只选能解释行为的测试，不全读

选择信号：

- 被最多模块 import 的文件（高扇入）
- 单文件 LOC 最大的前 10 个（复杂度集中点）
- 目录名包含 core/service/domain/client/adapter/registry
- 有专门设计文档或大量注释的模块
- 最近 6 个月改动最频繁的目录（用 `git log --name-only` 可查）

排除信号：

- 自动生成的代码、vendored 依赖、迁移脚本（除非是学习重点）
- 纯类型声明（先看结构，不必逐行）
- 一次性脚本、示例代码

## 2. 如何选核心流程

每个模块选 1-2 条，优先满足：

1. **用户可见**：一条命令/API 从进入到返回
2. **跨模块**：至少经过 3 个文件/2 个抽象层
3. **有分支**：包含权限、错误、重试、降级中的至少一种
4. **可验证**：能对应到测试或真实调用

推荐组合：

- 流程 A：**happy path**（正常主链路）
- 流程 B：**failure/recovery path**（403/超时/重试/回滚/降级）

不要选：

- 纯工具函数调用链（太短，学不到架构）
- 只有一行转发的 wrapper（除非它承载了关键契约）

## 3. 如何做逐段源码走读

每个代码锚点按四问写：

1. **做了什么**：输入、输出、状态变化
2. **为什么在这里**：为什么放在这一层，而不是上一层/下一层
3. **边界是什么**：空值、超时、并发、权限、截断、编码
4. **失败会怎样**：抛错/返回错误码/降级/重试，调用方如何感知

锚点格式统一为 `path/to/file.ext:line`（行号必须真实）。

一条流程建议 5-8 个锚点，覆盖：

```text
入口解析 → 参数校验 → 编排决策 → 外部 IO → 结果归一 → 错误映射 → 出口
```

深度校准：

- P0 文件：逐行读，标注关键分支
- P1 文件：读导出函数签名 + 主分支，跳过纯格式化代码
- P2 文件：只读注释与类型定义

## 4. 如何设计思考题

每题标注层级，避免是非题：

| 层级 | 目的 | 示例问法 |
|---|---|---|
| 事实 | 确认读到了 | 「这个字段在什么条件下为 true？」 |
| 机制 | 理解因果 | 「为什么先做 A 再做 B？反过来会出什么问题？」 |
| 设计 | 形成判断 | 「如果要支持 X，应该改哪一层？代价是什么？」 |
| 延伸 | 建立联系 | 「这个错误码和另一个模块的哪个处理是同一套契约？」 |

每个模块 3-5 题，至少覆盖 3 个层级。好题的特征：

- 答案能在源码中找到依据
- 需要跨 2 个以上文件才能答全
- 有一个「看似合理但错误」的直觉答案

坏题的特征：

- 「这个文件是做什么的？」（复述）
- 「你觉得这个设计好吗？」（无锚点）
- 能在 README 里直接抄到答案

## 5. 常见反模式

- **按目录顺序读**：应该按依赖顺序（先数据结构，再主流程，再边界）
- **逐行翻译代码**：应该解释意图与权衡
- **只读 happy path**：错误分支往往承载真正的设计
- **忽略测试**：测试是最好的行为说明书
- **忽略配置与启动**：很多行为由配置决定
- **一次排满 8 小时**：7 天计划应按 2-4 小时/天切分

## 6. 交付前验证

1. 运行 `scripts/check_refs.py <plan.md> --root <repo>`，确保所有 `path:line` 存在且行号在范围内。
2. 抽查 3 条流程：按计划顺序能否在不看其它资料的情况下走通。
3. 抽查 3 道思考题：答案是否能从标注的源码位置推出。
4. 检查每天内容量：是否超过 4 小时；超了就标注「选读」或后移。
